# Phase 2 第一部分：同步可靠性與效能

此階段以 Phase 1 PR 為基底，獨立 PR 交付。未宣稱私人 OAuth、介面本地化或實機驗收已完成。

## 已實作

- 仍下載公開 CSV 完整快照，但本機只 upsert 實際變更的教材，不再先軟刪除整個來源再重寫。
- 每批最多讀取 250 列；以穩定鍵查詢對應的本機教材，只比較這一批完整文字。相同批次重複 ID 取最後一列，跨批次也維持最後一列優先。
- 當次已見 ID 放在交易連線的 SQLite TEMP 表，讀取完整 CSV 成功後才以集合運算軟刪除缺少的列；已軟刪除的列不重複 UPDATE。TEMP 表在成功、格式錯誤或取消時皆清除。
- 每批比對時跳過沒有變更的教材；ID 唯一的相同快照不 UPDATE 教材。若重複 ID 跨越批次，可能先寫入中間值，最後仍以最後一列為準。學習進度與佇列不參與更新交易。格式錯誤即使發生在第一批寫入後，也會回復整個來源。
- 新增來源、移除來源、還原備份會遞增記憶體內的同步世代，讓先前已發出的 HTTP 回應失效；即使移除後以相同名稱、URL、穩定 ID 重新加入也不能被舊回應寫回。程序重啟後舊 HTTP 請求已不存在，因此不需將世代寫入備份或修改資料庫 schema。
- 取消 WorkManager 工作會取消正在等待回應或讀取內容的 OkHttp Call；下載途中每一批 buffer 也檢查網路政策與 coroutine 取消狀態。只接受 HTTPS，不跟隨 HTTPS 降級為 HTTP 的重新導向。
- 切換 Wi-Fi 政策立即取消舊排程並依新條件重新排程，啟動同步直接使用 Room 已保存的政策；其他手動同步仍以 KEEP 避免重複工作。僅 Wi-Fi 模式維持非計量約束，且另檢查 Wi-Fi transport。
- 教材庫顯示實際 WorkManager 狀態，以排程時間標籤選取最新工作，避免把舊工作結果當成這次同步結果。

## 自動化驗證範圍

一萬筆教材的首次匯入、相同快照重跑、只改一列及刪除一列；測試透過 SQLite trigger 計算實際 UPDATE 數量，並確認學習進度與其他來源不變。測試記錄耗時，但不把 JVM 耗時冒稱為手機效能或設置易受 CI 負載影響的固定時間門檻。

其他情境包括跨 250 列邊界的重複 ID、空快照、軟刪除後復原、批次之後才出現的錯誤、來源移除再加入、真實本機 HTTPS 伺服器、HTML／403／降級重新導向拒絕、取消沒有回應的 HTTP 請求，以及下載途中網路政策改變。
